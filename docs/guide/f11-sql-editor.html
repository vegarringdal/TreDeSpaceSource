SQL Editor

Bring your own tag data into the viewer: run saved reports, show the results as a table, colour or select the matching items in the model, and see the data of any item you click. Numbered markers on each picture match the numbers in the text; click a picture to see it full size.

On this page

App layout · F11

The SQL Editor layout

Press F11 (or pick SQL Editor on the App Layout ribbon) to switch to the SQL workspace. It is built for working with a database that describes the items in your model — for example a tag register with status, area and documents for every tag. Most people only use the Sql Report panel: pick a saved report, press a button, and look at the result. The SQL Editor is for writing and testing new reports.

  1. Home ribbon — the same ribbon as in F1 Home. Its SQL button (ALT 631) opens SQL Assets, where databases are imported.
  2. Hierarchy — the model tree. Clicking an item here selects it, and the SQL Detail panel shows its data.
  3. Sql Report (SQL Reports) — the saved reports of a store. Described below.
  4. SQL Editor — write and test your own SQL. Described below.
  5. 3D view — shows the colouring and selection made from SQL results. Click an item to see its data in SQL Detail.
  6. SQL Table — the result of a report as a table. Described below.
  7. Console — messages. The SQL Editor's Run button writes its result rows here.
  8. SQL Detail — the data of the item you clicked, as a form. Described below.

Ribbon

The ribbon

This layout uses the Home ribbon. It is described on the F1 Home page. The one button you need here is SQL in the Assets group: it opens the SQL Assets panel, where you import a database (see Get your database into the app).

Before you start

How the data is linked to the model

The viewer does not need to know anything about your database. The link is made by name: if a column in the result is called fullname and holds the name of an item exactly as the Hierarchy shows it, for example /SX-HA86-011A, the viewer can find that item in the model.

Words used on this page

  • Database — a SQLite file (.db, .sqlite, .sqlite3, .db3). It holds tables; a table has columns (fields) and rows (one per tag, for example).
  • Store — a named project that groups models and databases. Every database is imported into a store, and every report belongs to a store. A new installation has one store, main.
  • SQL — the language used to ask a database a question. A query such as SELECT tag, status FROM tags WHERE area = 'Main deck' returns a result: a small table.
  • Report — a saved query with a name, a description and optional input fields (filters), so it can be run with one click by people who do not write SQL.
  • fullname — the result column that links a row to a model item. The whole name must match, including the leading /; capital letters do not matter. A match takes the item and everything under it, the same way a click in the tree does.
  • fullname_color — an optional result column with the colour for that row (see Colours in a result).

A report can be used in three ways. These are its Types:

  • TABLE — show the result rows in the SQL Table panel.
  • COLORING — colour, isolate or select the items named in the fullname column.
  • DETAIL — every time you select an item, run the query for that item and show the answer as a form in SQL Detail.

The pictures on this page use a small example database, huldra-tags.db, made up for this guide from the names in the Huldra sample models. It has a tags table (fullname, tag, description, discipline, system, area, status, install_date, datasheet_url) and a documents table (tag, doc_no, title, url). Your own database will have other tables and columns.

Step by step

Common tasks

Get your database into the app

  1. On the Home ribbon, press SQL (ALT 631). The SQL Assets panel opens.
  2. Choose the store under Import to (the store your models are in), then press Import Database and pick the file. The database is copied into the browser's own storage, so it is there next time you open the app.
  3. Back in F11, choose that store in the Store list at the top of the Sql Report panel. Its reports are listed below it.

The F12 Assets page describes SQL Assets in full (deleting and replacing databases, stores).

Run a report and look at the result

  1. In Sql Report, pick the Store, then click a report's name to open it.
  2. Fill in its filters, if it has any. Here the Discipline list 2 already has Telecom picked.
  3. Press Table 3. The result appears in the SQL Table panel. Sort, filter and export it there (see SQL Table).

Colour the model from a report

  1. Open a report that has the COLORING type, here Tag status, and press Coloring.
  2. A box shows how many rows came back and asks how to use them. Press White: the whole model turns white and every tag gets the colour of its status.
  3. Press Hidden instead to see only the result: everything else is hidden. Here the Telecom tags from Tags by discipline, in yellow because that report has no colour column.
  4. To go back, press Undo (PAGEUP) — every colouring is one undo step — or Clear All (ALT+R, see F4) to remove all colours and hiding.

Select the result and fly to it

  1. Run the report's Coloring and press Selection. Every item in the result becomes the selection; colours are not changed.
  2. In the Hierarchy, press Fly to selection (ALT 625) to zoom to the selected items. Here the tags installed since 1 September 2025 (Installed since).

Clicking rows in the SQL Table does not select anything in the model — it only marks rows for copying and export. To select the items of a result, use Selection (or Color Selection).

See the data of the item you click

  1. Open a report with the DETAIL type, here Tag card, and press Detail. The SQL Detail panel now follows your clicks.
  2. Click an item in the 3D view or in the Hierarchy. Its data is shown as a list of fields; web addresses are links.
  3. Click the next item — the form follows. Press Listening to pause it (it then reads Paused).

Write and test your own query

  1. In the SQL Editor, choose the database under Main db.
  2. Type the SQL, for example SELECT discipline, status, count(*) AS tags FROM tags GROUP BY discipline, status.
  3. Press Run (Ctrl + Enter in the SQL box). The rows are written to the Console, and the line at the bottom of the editor says how long it took and how many rows came back.
  4. Press As Table to see the same result in the SQL Table.

If the result has a fullname column, the colour buttons (Color White, Color Hidden …) work on it straight away, just like a report's. A good first query to explore an unknown database is the one the editor starts with: SELECT name, type FROM sqlite_master ORDER BY name; — it lists every table.

Save your query as a report

  1. Give it a Name and a Description in the SQL Editor, and tick the Types it should offer.
  2. Press Save Local (ALT 660). The report is added to the store of the Main db, and the Sql Report panel switches to that store so you can see it. Without a name you are asked for one; without a Main db the button is greyed out.

To change an existing report, use its pencil button in Sql Report (see Edit a report). To work on it in the bigger editor, press Set editor there; Save Local then saves a new report and leaves the original as it was.

Let users pick a value: add a filter

  1. Edit the report and press Add filter. A filter has a key (the name the SQL uses) and a Label (what the user sees).
  2. Choose Input for a text box, or Dropdown for a list filled by its own small query.
  3. In the report's SQL, read the value with (SELECT v FROM FILTER_ARGS WHERE k = 'your key'). See Filters in SQL for ready-made patterns.
  4. Test with the Test buttons, then Save.

Panel

Sql Report (SQL Reports)

The saved reports of one store. Its tab reads Sql Report; open it on its own from the Panels ribbon (ALT 679).

  1. Store — reports are kept per store. Nothing is listed until a store is picked.
  2. New report — creates an empty report called “New report” in this store, saves it and opens it for editing.
  3. Search reports… — shows only reports whose name or description contains the text.
  4. A report — click its name to open it. The badge shows its types. Only one report is open at a time.
  5. Edit (pencil) — opens the report for editing. This is the only place its SQL is shown.

Run a report

  1. Description — written by whoever made the report.
  2. Filters — text boxes or lists. They start with the report's saved values; what you change is used when you run it, but it is not saved into the report.
  3. Table — runs the report and shows the result in SQL Table.
  4. Coloring — runs the report and asks how to apply the result (below).

A report with the DETAIL type also has a Detail button: it connects the report to the SQL Detail panel. Table and Coloring are greyed out while a report is running.

Apply a coloring result

  1. How many rows came back. Rows whose fullname is not in the loaded model are ignored.
  2. Set color — runs your current Set Color rules, with the result added as one more rule on top. The Set Color panel itself is not changed.
  3. White — everything white, the result in its colours.
  4. Hidden — only the result is shown, in its colours; everything else is hidden.
  5. Transparent — like White, but the rest of the model is white at 10 % opacity, so it stays faintly visible.
  6. Selection — selects the result instead of colouring it.

Rows without a colour are yellow. The colour choices clear earlier colours first, except Set color, which follows the run mode of your Set Color rules (see Run modes). Every colouring can be undone in one step with Undo (PAGEUP).

Edit a report

Press the pencil on a report. The report opens as a form; nothing is saved until you press Save.

  1. Name — shown in the list.
  2. Description — shown above the filters. **bold** and new lines work.
  3. Main db — the database the report reads. The list holds the databases of this store. (None — attach only) is for reports that bring in their databases with ATTACH (see Using two databases).
  4. Types — which buttons the report gets: COLORING, TABLE, DETAIL.
  5. SQL — the query. Drag the bottom-right corner to make the box bigger. The ⓘ button next to the label sums up the rules from Writing SQL for the viewer.
  6. As Table — runs the form as it is now, unsaved changes included, and shows it in SQL Table.
  7. Color White, Color Hidden, Color Transparent, Color Set, Color Selection — test the colouring directly (the same as the choices above).
  8. As Detail — connects the unsaved form to SQL Detail.
  1. Add filter — adds a text box filter. The two arrow buttons beside it open or fold all filters.
  2. Input / Dropdown — a text box, or a list of values to pick from. The header of each filter has buttons to move it up or down (the order the boxes are shown in) and to remove it.
  3. key — the name the SQL reads the value by.
  4. Label — the text shown beside the box. Without it, the key is shown.
  5. Input: the default value. Dropdown: the search default, used while the user has not typed anything — normally % (“anything”).
  6. Dropdown SQL — the query that fills the list. Name its columns id (the value passed on) and label (the text shown); a ? stands for what the user types. The list shows the first 25 matches.
  7. Single select — the user picks one value instead of several.
  8. Test/selected — try the list here. What you pick is saved as the report's pre-selected value.
  9. Save — saves the report. Cancel throws the changes away.
  10. Set editor (ALT 661) — copies the form, unsaved changes included, into the SQL Editor (it asks first, because it replaces what is there). Delete removes the report after asking.

Reports are stored in the store's own file, SQL_Reports.json, next to its databases in the browser storage. Anyone using the app in this browser sees the same reports.

Panel

SQL Editor

A workbench for SQL. It holds one draft report — name, description, types, SQL and filters — that you can run, test against the model and save as a report. Open it on its own with ALT 632.

  1. Clear (ALT 658) — empties the editor: name, description, SQL, filters and types. It asks first. The Main db stays.
  2. Save Local (ALT 660) — saves the draft as a new report in the Main db's store. Greyed out until a Main db is picked.
  3. Main db — the database to query, from any store. Assets next to it opens SQL Assets.
  4. Types — which of the buttons below are enabled: the colour buttons need COLORING, As Table needs TABLE, As Detail needs DETAIL.
  5. The SQL box — Ctrl + Enter runs, Tab / Shift + Tab indent. Highlight part of the text and every button runs only that part — handy when the box holds several queries.
  6. Run (ALT 635) — runs every statement. The result rows are written to the Console.
  7. Shared / Exclusive (ALT 636) — Shared (the normal setting) only reads, and several tabs can read at once. Exclusive also allows changing the database (INSERT, UPDATE, CREATE TABLE …), one tab at a time. Reports always run Shared.
  8. Kill (END while a query runs) — stops a query that takes too long.
  9. Color White (ALT 644), Color Transparent (ALT 1220), Color Hidden (ALT 645), Color Set (ALT 646), Color Selection (ALT 1291) — colour or select the result, as described in Apply a coloring result. Color Selection writes to the Console how many names were found and how many are not in the model.
  10. As Table (ALT 643) — shows the result in SQL Table. As Detail (ALT 647) — connects the SQL to SQL Detail (see the tip below).
  11. Filters — the same filter editor as in a report (see above). Run uses their values too.
  12. Will lock — the database files the next run opens. A red name is not in SQL Assets: a Shared run will fail, an Exclusive run creates an empty database with that name.
  13. Status — ready, running…, the time and row count of the last run, or the error message.

As Detail in the editor helps you: if the SQL does not use TREE_VIEW_ARGS, it is automatically limited to the row whose fullname is the clicked item. A report's Detail button does not do this — a saved DETAIL report must use TREE_VIEW_ARGS itself, or it shows the same first row for every click (see Detail queries). Alt + click on As Detail or Detail writes the SQL it connected to the Console.

The editor keeps its contents when you switch layout or close the panel, but not when the app is reloaded. Save anything you want to keep with Save Local.

Panel

SQL Table

Shows the result of the last Table / As Table run. A new result replaces the old one and resets sorting, filters and the row selection.

  1. Row count — “21 of 50 rows” while column filters hide some. With rows marked, a badge shows how many.
  2. Load all (ALT 653) — a report shows its first 50 rows only. Load all runs it again for up to 250,000 rows. The button is only there when the result was cut off.
  3. Clear on close / Keep (ALT 662) — whether closing the panel throws the result away (the default, to free memory) or keeps it for when you open the panel again. Switching layout never throws it away.
  4. Column title — click to sort A→Z, again for Z→A, a third time to unsort. Drag the edge of a title to change the column width.
  5. filter… — shows only rows whose value in that column contains the text (capitals do not matter). Filters in several columns must all match.
  6. Row number — click to mark a row, Ctrl + click to add or remove one, Shift + click for a range.
  7. Corner box (ALT 652) — marks every row shown, or unmarks them all.

Right-click in the table for export and copy:

  • Export to Excel (all) (ALT 654) / (selected rows) (ALT 655) — downloads an .xlsx file.
  • Copy to clipboard (all) (ALT 656) / (selected rows) (ALT 657) — tab-separated with a header row, ready to paste into a spreadsheet.

Both take the rows as shown: column filters and sorting are applied. The “selected rows” entries are greyed out until rows are marked.

Panel

SQL Detail

Shows one row of data for the item you selected last, as a list of fields. It needs a report: press a report's Detail button, or As Detail in the SQL Editor. Until then it says “No report bound”.

  1. Listening / Paused (ALT 651) — while Listening, every selection — a click in the 3D view or the tree, or U / P to walk up and down the tree — runs the report for that item. Paused keeps the current form.
  2. Filter fields… — shows only the fields whose name or value contains the text.
  3. Hide empty — on by default: fields without a value are left out (here the install date of a tag that is not installed yet).
  4. Links — a value that is a web address opens in a new browser tab.
  5. Lists — a column that holds a list (several documents, for example) is shown as one field per entry.

If the query finds nothing for the item, the panel says No data found for and the item's name. The panel forgets its report when the app is reloaded — press the report's Detail button again.

For report writers

Writing SQL for the viewer

The viewer uses SQLite. Any SQLite query works; a few rules decide how the result is used. If a query has several statements (separated by ;), the last one gives the result; the ones before it run first (for example to ATTACH a database).

Colours in a result

For colouring, the result needs a fullname column. An optional fullname_color column gives each row its colour: a colour name (red), a hex code (#1c7ed6) or default (the item's own colour). Add :50 for 50 % opacity (red:50). Rows without a colour are yellow. Other columns are ignored, so the same query can also be a TABLE. This is the Tag status report: 

SELECT fullname,
       CASE status
         WHEN 'Commissioned' THEN 'green'
         WHEN 'Installed'    THEN '#1c7ed6'
         WHEN 'Punch open'   THEN 'orange'
         ELSE 'red'
       END AS fullname_color,
       tag, status, install_date
FROM tags
ORDER BY status, tag;

CASE … WHEN … THEN … END picks a value by condition, and AS fullname_color names the column.

Filters in SQL: FILTER_ARGS

Before the report runs, the viewer puts the filter values into a small temporary table called FILTER_ARGS with two columns: k (the filter's key) and v (the value). A dropdown with three values picked gives three rows; an empty text box gives none. The Installed since report reads one value: 

SELECT fullname, tag, description, install_date
FROM tags
WHERE install_date >= (SELECT v FROM FILTER_ARGS WHERE k = 'since')
ORDER BY install_date;

The Tags by discipline report takes several picks, and everything when nothing is picked:

SELECT fullname, tag, description, discipline, system, area, status
FROM tags
WHERE discipline IN (SELECT v FROM FILTER_ARGS WHERE k = 'discipline')
   OR NOT EXISTS (SELECT 1 FROM FILTER_ARGS WHERE k = 'discipline')
ORDER BY tag;

Its Discipline dropdown is filled by:

SELECT DISTINCT discipline AS id, discipline AS label
FROM tags WHERE discipline LIKE ? ORDER BY 1

LIKE ? compares with what the user types in the list's search box (% means “anything”).

Detail queries: TREE_VIEW_ARGS

When you select an item, the viewer fills a second temporary table, TREE_VIEW_ARGS, with one column FULLNAME: the selected item first, then its parent, and so on up to the top folder of the tree. Joining your table to it finds the most specific match — so clicking a small part inside a tagged item still shows the tag. The Tag card report: 

SELECT t.tag, t.description, t.discipline, t.system, t.area, t.status,
       t.install_date, t.datasheet_url AS datasheet,
       (SELECT json_group_array(json_object(
                 'label', d.doc_no, 'value', d.url, 'value_link_label', d.title))
          FROM documents d WHERE d.tag = t.tag) AS documents
FROM TREE_VIEW_ARGS a
JOIN tags t ON lower(t.fullname) = lower(a.FULLNAME)
ORDER BY a.rowid;
  • Only the first row is shown, so ORDER BY a.rowid puts the clicked item before its parents.
  • The field names are the column names — use AS to rename them (datasheet_url AS datasheet).
  • A column built with json_group_array(json_object('label', …, 'value', …, 'value_link_label', …)) becomes one field per entry: label is the field name, value the value and value_link_label the link text when the value is a web address.
  • TABLE and COLORING runs also get TREE_VIEW_ARGS, filled from the last selection — so a report can work on “what I selected”.

Using two databases

A report can read more databases than its Main db with ATTACH. The path is sql_assets/<store>/<file name>, as shown under Will lock in the SQL Editor: 

ATTACH DATABASE 'sql_assets/main/punchlist.db' AS punch;
SELECT t.fullname, 'orange' AS fullname_color, t.tag, p.description
FROM tags t
JOIN punch.items p ON p.tag = t.tag;

Here punchlist.db stands for a second database of your own with an items table; AS punch is the short name its tables are read by.

With (None — attach only) as Main db, a report can work from attached databases only.
